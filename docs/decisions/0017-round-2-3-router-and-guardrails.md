# ADR 0017: Subject before intent, a trained intent classifier, blocking injection, the visitor's own key

Status: accepted (2026-10-01). Supersedes the routing part of ADR 0013.

## Context

The static demo has no model, and visitors type like people do: informal Portuguese, no accents,
typos, long messages, questions about colleagues and teams. Round 2 extended the lexical router
of ADR 0013 (shared lexicon, cite-or-refuse knowledge gate, injection blocked before any model or
tool, live mode with the visitor's own OpenRouter key). A hidden battery in round 3 showed three
classes of failure: questions about someone else answered with the speaker's own data, personal
questions falling to the knowledge base, and a lexical router that generalizes poorly (28/40 on a
blind set).

## Decisions

### Subject before intent (round 3)
`runtime/subject.py` (and `subject.ts`) decides whose data a message asks for before routing: a
named colleague, the speaker's manager, the speaker's team, a group (role, area, colleagues, an
average) or everyone. A domain word counts for someone else only when it is attached to them
("a folha de pagamento do time", "salário médio dos analistas", "every salary"). The policy engine
decides (`authorize` for a person, `authorize_scope` for team, group and company); refusals are
audited and offer the speaker's own data. Underneath, `execute()` refuses every self-service tool
in a turn whose subject is not the speaker (`subject_mismatch`), whatever a router or a model picks.
Rule, enforced by `shared/eval/subject.yaml` in both engines: a question about someone else is never
answered with the speaker's data.

### Intent classifier blended with the profiles (round 3)
A linear model over hashed words, word pairs and character n-grams (`runtime/intent.py`, integer
weights and one square root, so Python and the browser compute bit-identical scores), blended with
each agent's lexical profile score (BLEND 1.5). Deterministic rules stay above it: subject check,
injection and sensitive topics, life events, general requests, request ids, the manager team rule,
follow-ups. Studio agents the classifier never saw win on their profile when clearly ahead.
Compound questions call a second specialist only for a clause that names its topic; short margins
ask "Você quis dizer..." with examples of the close candidates only. Answers that find nothing end
with questions of the probable domain and an HR ticket.

The suggested direction was a training set generated by a model. The generation run spent this
step's budget (US$ 0.205 against a US$ 0.20 cap, reasoning tokens on by default) and was killed by
a shell timeout before writing anything. No more was spent; the generator now persists every call and enforces a
budget across runs. The training set is model-free instead: a grammar written from the catalog, the
knowledge base's FAQ questions and the catalog examples, with writing noise. Its author had seen
both blind sets, so the trainer drops every template with an expansion near a blind question and
every near item (3 shared tokens at Jaccard >= 0.4, or a shared non-vocabulary word triple), on top
of the 0.6 overlap guard against every evaluation set. Constants were frozen on the tuning sets
before the blind sets were measured once.

### Which retrieval hit answers (round 3)
The answer still comes from the first retrieval hit that covers enough of the question
(`MIN_CITED`), but equal retrieval scores no longer fall to document order: the hit covering more
of the question goes first. Swapped vector and full-text ranks give exactly equal fused scores, and
document order had made the absences table answer "Posso vender 10 dias de férias?" because it
holds "dias" and "férias". A near tie is left to retrieval, which carries meaning that lexical
coverage does not. Excerpts no longer end a sentence at "art.", which had cut "(CLT, art. 143)."
in half.

### Catalog agents carry the risk of their tools (round 3)
Studio agents were labelled high risk when any tool writes or is sensitive; catalog agents were
seeded without a label and read as low risk even with write tools. One `agent_risk` rule per engine
now labels both, at the seed and at Studio validation.

### Injection blocks (round 2, widened in round 3)
Strong signals (override, admin or developer claims about this assistant, system-style prefixes,
fake markup, prompt exfiltration, bulk exfiltration, guardrail bypass, in PT, EN and ES) block the
message before any model or tool; role-play alone only warns. No shipped knowledge chunk may match
a pattern, because a flagged chunk quarantines its document.

### Live mode with the visitor's key (round 2)
The demo can use the visitor's own OpenRouter key: kept in sessionStorage only, sent only to
openrouter.ai (CSP `connect-src`), `max_tokens` on every call. The model routes, picks tool calls
and writes text; argument validation, the policy engine, proposals and guardrails stay in the
browser engine.

## Consequences
- Blind accuracy is an upper bound: the grammar's author had seen both blind sets, despite the
  guard. The owner's hidden battery is the real test.
- The trained model is a committed artifact (`shared/generated/intent-model.json`, 158 KB gzip);
  `atrium train-router` rebuilds it, and tests keep the training set reproducible and guarded and
  the model tied to it by hash.
- Adding an evaluation question can drop training items through the guard; retraining then changes
  the router, which has to be measured again.

## Alternatives rejected
- Replacing the rules with the classifier: subject, injection and life events must stay
  deterministic and explainable.
- Embeddings in the browser: a model download per visitor and no bit-identical parity.
- A model-generated set seen once and then edited by hand: no reproducibility.
